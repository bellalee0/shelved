## 저장소 구조

프론트엔드와 백엔드를 하나의 저장소에서 관리한다.

```plain text
shelved
├── backend/             # Spring Boot
├── frontend/            # React + Phaser (TypeScript)
├── docs/
│   ├── api/             # 사전 설계 API 명세 (구현 전에 작성)
│   ├── conventions/     # 컨벤션 문서 (common / backend / frontend)
│   └── wireframes/      # 화면 와이어프레임 (저충실도 HTML, 가상 예시 데이터만 사용)
├── AGENTS.md            # AI 에이전트 진입 파일 (Codex, 안내 내용 원본)
├── CLAUDE.md            # AI 에이전트 진입 파일 (Claude Code, AGENTS.md를 불러옴)
└── README.md
```

- 영역별 코드는 반드시 `backend/` 또는 `frontend/` 하위에 둔다. 루트에는 저장소 전체에 적용되는 파일만 둔다.
- 컨벤션은 `docs/conventions/`에만 작성한다. 에이전트 진입 파일에는 규칙을 직접 쓰지 않고 이 문서들을 가리키기만 한다.

### 로컬 전용 파일

아래 파일은 정답·원작 정보를 포함하므로 `.gitignore`로 제외하고 저장소 소유자의 로컬에만 둔다.

| 경로 | 내용 |
|---|---|
| `project-spec.md` | 세부 기획서 |

| `backend/src/main/resources/dev-data/` | 개발용 실제 사건 데이터(시드) |

## 정답 정보 보호 (공개 저장소)

이 저장소는 공개 저장소이며, 게임의 핵심은 플레이어가 원작과 정답을 모른 채 수사하는 것이다. 따라서 **저장소에 올라가는 모든 것**에 실제 사건의 정답을 넣지 않는다.

- 대상: 코드, 주석, 테스트 픽스처, 커밋 메시지, PR 제목·본문, 브랜치명, README, 에셋 파일명·메타데이터
- 금지 정보: 사건 카드와 원작 소설의 대응, 범인, 트릭, 채점 기준, NPC 내부 설정(숨기는 사실·정해진 거짓말)
- 테스트와 예시에는 실제 사건 대신 가상의 사건·인물을 사용한다. (예: 기획서 3.2절의 "녹음기·집사" 예시처럼 설명용으로 지어낸 내용)
- 실제 사건 데이터가 필요한 개발용 시드는 [로컬 전용 파일](#로컬-전용-파일) 경로에 둔다.
- 원작 원문(`.txt`)은 퍼블릭 도메인이지만 어떤 소설을 쓰는지 드러나므로 저장소에 넣지 않는다.

## 비밀 값 및 로그 관리

- 로컬 API 키·DB 비밀번호·JWT 서명 키 등 비밀 설정은 Git에서 제외한 `.env`에 두고 실행 시 환경 변수로 주입한다. `.env` 파일이 모든 도구에서 자동으로 로드된다고 가정하지 않으며 실제 주입 방법은 README에 기록한다.
- `.env.example`에는 변수명·용도와 가짜 예시 값만 기록한다. 실제 비밀 값을 복사하지 않는다. 프론트엔드 `VITE_` 변수에는 공개 가능한 설정만 넣는다.
- 원작 전문·NPC 내부 설정·정답·개인 노트는 `.env`에 옮기지 않는다. 기존 데이터 저장 위치와 접근 권한을 유지한다.
- `.env` 사용과 로그 보호는 별개다. 토큰·API 키·인증 헤더·원작 전문·내부 프롬프트·정답·개인 노트 전문을 애플리케이션 로그, 브라우저 콘솔, 테스트 출력에 남기지 않는다. HTTP 클라이언트·SQL 바인딩 등 디버그 로그도 같은 기준을 따른다.
- 로그는 요청 식별자, 처리 시간, 상태, 오류 코드 중심으로 남긴다. 요청·응답 전체나 환경 변수 전체를 출력하지 않고, 필요한 경우 민감한 필드를 제거하거나 마스킹한 뒤 기록한다.

## Git 브랜치 전략

### 브랜치 구조

```plain text
main          # 시연·배포 가능한 안정 버전
 └─ dev       # 개발 통합 브랜치
     ├─ feat/be-npc-ask
     ├─ feat/fe-npc-dialog
     └─ feat/npc-ask
```

- 새 작업은 코드·문서 수정 전에 반드시 `dev`에서 전용 작업 브랜치를 생성한다. 같은 작업을 이어갈 때는 해당 브랜치를 재사용하며, PR은 `dev`를 대상으로 한다.
- 작업 전 현재 브랜치와 `git status`를 확인하고, 기존 미커밋·미추적 파일을 자신의 변경과 구분한다. 다른 작업자의 수정은 임의로 되돌리거나 덮어쓰거나 자신의 커밋에 포함하지 않는다.
- 브랜치는 커밋 이력을 분리하지만 같은 폴더의 미커밋 파일까지 격리하지 않는다. 같은 폴더에서 여러 작업을 동시에 진행하며 브랜치를 전환하지 않는다. 병렬 작업이 필요하면 작업별 별도 체크아웃 또는 worktree를 사용한다.
- 기존 변경을 없애기 위한 강제 체크아웃·`reset --hard`·`clean`을 실행하지 않는다. 변경이 있는 상태에서 브랜치를 전환할 때는 기존 파일이 보존되는지 확인한다.
- `dev`는 시연·마일스톤 단위로 `main`에 병합한다.
- `main`, `dev`에는 직접 커밋하지 않는다.
- 프론트엔드/백엔드 전용 통합 브랜치(`front`, `back` 등)는 두지 않는다. API와 화면이 함께 바뀌는 기능은 하나의 브랜치에서 작업한다.

### 브랜치 명명 규칙

```
{type}/{scope}-{작업 내용}

example: feat/be-npc-ask / feat/fe-case-list / feat/npc-ask / docs/conventions
```

- `type`은 [커밋 유형](#커밋-유형)과 동일하다.
- `scope`는 `be`(백엔드) 또는 `fe`(프론트엔드)이다. 두 영역을 함께 변경하거나 어느 영역에도 속하지 않으면 생략한다.
- 작업 내용은 도메인 + 기능 중심으로 짧게 쓴다.

## Git 커밋 메시지 컨벤션

### 커밋 유형

| 커밋 유형 | 의미 |
| --- | --- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 코드 리팩토링 |
| `test` | 테스트 코드 추가·수정 |
| `docs` | 문서 수정 |
| `chore` | 빌드·설정·의존성 등 기능과 무관한 수정 |
| `release` | 릴리즈 |

### 형식

```
{type}({scope}): 제목

- 변경사항 1
- 변경사항 2
```

```
example:
feat(be): NPC 자유 질문 API 추가

- 요청 식별자(request_id)로 중복 요청 처리
- 직접적인 정답 요구 질문은 AI 호출 전에 차단
```

- `scope`는 `be` / `fe`를 사용하며, 영역에 속하지 않는 변경(문서, 루트 설정 등)은 생략한다. (예: `docs: 공통 컨벤션 추가`)
- 한 커밋에는 한 영역의 변경만 담는다. 같은 기능이라도 백엔드와 프론트엔드 변경은 커밋을 나눈다.
- 제목: 커밋 유형 + 요약
- 본문: 변경한 내용과 이유를 설명하고, 여러 항목이면 글머리 기호를 사용한다.
- 커밋은 최소 단위로 진행한다.

## Pull Request 규칙

### PR 단위

- 최소 단위로 생성한다. API 하나, 화면 하나처럼 기능 단위가 이상적이다.
- API와 그 API를 사용하는 화면을 함께 만든 경우 하나의 PR로 올릴 수 있다. 이때도 커밋은 영역별로 나눈다.

### PR 제목

커밋 메시지 제목과 같은 형식을 사용한다.

```
example: feat(be): NPC 자유 질문 API 추가
```

### 검토 및 병합

- PR은 저장소 소유자가 직접 확인한 뒤 승인·병합하거나 수정을 요청한다.
- AI 에이전트는 PR 생성까지만 수행하며, 직접 병합하지 않는다.

### PR 템플릿

여러 에이전트가 서로 다른 대화창에서 작업하므로, PR은 **다음 작업자가 맥락을 이어받는 기록**의 역할을 한다. 설계 변경, Breaking Change, 다음 작업자가 알아야 할 점은 생략하지 않고 작성한다.

```plain text
## ✨ PR 요약
> 이 PR이 해결하는 문제를 한 줄로 설명해주세요

## 🗂 변경 영역
- [ ] Backend
- [ ] Frontend
- [ ] 공통 (문서, 설정 등)

## 📋 변경 내용
-
-

## 🧱 설계 / 구조 변경
- 변경된 패키지·폴더 구조
- 도메인 / 레이어 변경 여부
- 새로 도입한 라이브러리·패턴

## 🧪 테스트 결과
- 테스트 종류:
  - [ ] 단위 테스트
  - [ ] 통합 테스트
  - [ ] 화면 직접 확인
  - [ ] 수동 플레이테스트 (기록은 로컬 `playtest/`에 작성)
- 테스트 결과 요약:

## 🖼 화면 캡처 (Frontend 변경 시)

## 🚨 Breaking Change
- [ ] 있음
- [ ] 없음

> 있다면 상세 설명 (무엇이 바뀌었고, 기존 코드·데이터에 어떤 영향이 있는지)

## 📌 다음 작업자가 알아야 할 점
> 미완성 부분, 임시 처리, 후속 작업, 이 PR에서 내린 결정과 그 이유
```

### Breaking Change 기준

기존 호출자·저장 데이터·설정이 수정 없이 동작할 수 없게 되는 변경만 Breaking Change로 표시한다.

- 예: 사용 중인 API 필드·경로 삭제 또는 타입 변경, 기존 데이터와 호환되지 않는 제약 추가, 필수 설정 키 변경, 사용 중인 이벤트·에셋 식별자 제거
- 기존 호출과 데이터가 그대로 유효한 선택 필드·테이블 추가, 내부 리팩터링, 호환되는 공통 컴포넌트 개선은 일반 설계/구조 변경으로 기록한다.
- 컨벤션 문구 보완 자체는 Breaking Change가 아니다. 기존 구현·실행 방법을 변경해야 하는 규칙 개정인 경우에만 표시한다.
- DB 변경은 호환 여부와 별개로 데이터 영향·적용 방법을 기록한다. API 명세도 실제 변경과 함께 갱신한다.

PR 본문도 공개되므로, Breaking Change와 "다음 작업자가 알아야 할 점"을 쓸 때도 [정답 정보 보호](#정답-정보-보호-공개-저장소) 규칙을 지킨다.

## API 명세

백엔드와 프론트엔드를 병렬로 개발하기 위해, API는 **구현 전에 명세를 먼저 작성**하고 양쪽 모두 이 명세를 기준으로 개발한다.

| 구분 | 사전 설계 명세 (`docs/api/`) | Swagger UI |
|---|---|---|
| 작성 시점 | 구현 전 | 구현 후 자동 생성 |
| 역할 | 백엔드·프론트엔드가 함께 따르는 계약, API의 기준 | 구현된 API 호출·확인, 명세와 일치하는지 검증 |
| 작성자 | 사람·에이전트가 직접 작성 | springdoc이 코드에서 생성 |

### 작성 절차

1. 기능 구현 전에 해당 API 계약을 `docs/api/`에 작성한다. 작은 MVP 기능·변경은 명세와 구현을 같은 브랜치·PR에 포함할 수 있으며 별도 명세 PR의 선행 병합을 요구하지 않는다.
2. 여러 작업자가 독립적으로 구현해야 하는 등 계약을 먼저 확정할 필요가 있을 때만 명세 PR을 분리한다. 이 경우 소유자가 검토·병합한 계약을 기준으로 구현한다.
3. 구현 중 계약 변경이 필요하면 명세부터 갱신하고 관련 구현을 같은 PR에서 맞춘다. 기존 호환성을 깨는 경우에만 Breaking Change로 표시한다.

### 명세에 담을 내용

- 메서드·경로, 인증 필요 여부(일반 사용자/관리자)
- 경로·쿼리 파라미터, 요청 본문 필드 (이름, 타입, 필수 여부, 제약 조건)
- 성공 응답: 상태 코드와 `CommonResponse`의 `data` 필드 구조
- 실패 응답: 상태 코드와 `ErrorCode` 이름·메시지
- AI 요청 API는 `request_id` 처리, `202 Accepted`·`409 Conflict` 조건
- 요청·응답 예시 (가상의 사건 데이터만 사용)

### 형식

- Markdown으로 작성하고 도메인별로 파일을 나눈다. 파일 구성, 공통 응답 형식, 상태 코드, 헤더 규칙은 [docs/api/README.md](../api/README.md)에 있다.
- 필드명은 백엔드 DTO와 프론트엔드 타입에 그대로 쓰일 이름(camelCase)으로 적는다.
- 예외 코드는 [docs/api/errors.md](../api/errors.md) 한 곳에 모은다. 새 코드를 추가하면 이 파일에 먼저 적는다.

## 포맷 및 검증 실행

- 초기 프로젝트 설정 시 루트 `.editorconfig`에 UTF-8·LF·마지막 개행과 영역별 들여쓰기(Java 4칸, TypeScript/JSON/YAML 2칸)를 고정한다. 포맷터 설정도 같은 기준에 맞춘다.
- 백엔드는 공유 IDE 코드 스타일 한 가지를 저장소에 두고 사용한다. 프론트엔드는 ESLint·Prettier 설정을 저장소에서 공유한다. 문서만 수정하는 작업에서 아직 없는 빌드 도구를 새로 설치할 필요는 없다.
- Gradle Wrapper(스크립트·설정·JAR)와 `frontend/package-lock.json`을 커밋 대상으로 관리한다. npm 설치는 잠금 파일 기준의 `npm ci`로 재현한다.
- 초기 설정 시 백엔드 `./gradlew test`, `./gradlew build`와 프론트엔드 `npm run lint`, `npm run typecheck`, `npm run test -- --run`, `npm run build`를 실행 가능하게 구성하고 README에 작업 디렉터리와 함께 기록한다.
- 변경한 영역의 관련 테스트·타입 검사·빌드를 수행한다. 문서만 변경하면 링크·예제·규칙 일관성을 확인하며, 영향 없는 전체 테스트를 반복하지 않는다. 실행하지 못한 검증은 이유와 함께 명시한다.

## 완료 보고 기준

- 작업 종료 시 무엇을 변경했고 왜 변경했는지, 실제 수행한 검증과 결과, 남은 문제·미검증 항목을 구분해 보고한다.
- 실행하지 않은 테스트를 통과했다고 표현하지 않는다. 실행이 불가능했다면 이유를 적고, 문서 검토·수동 확인·자동 테스트 결과를 구별한다.
- 기능 작업이면 `dev-checklist.md` 갱신 여부도 보고한다. 부분 완료는 전체 완료로 표현하지 않는다.
- 보고는 변경 규모에 맞게 간결하게 작성하고, 수정한 핵심 코드는 대화 안의 코드 블록으로 보여준다.

## AI 에이전트 작업 원칙

- 작업 전에 이 문서와 작업 영역의 컨벤션 문서(`backend.md` / `frontend.md`)를 먼저 읽는다.
- 게임 규칙·정책은 기획서(`project-spec.md`)를, 코드 작성 방식은 컨벤션 문서를 따른다. 둘이 충돌하면 임의로 한쪽을 고르지 않고 저장소 소유자에게 묻는다.
- 기획서의 필드명·엔드포인트·ERD는 초안이다. 구현 중 더 적합한 이름·구조가 보이면 소유자와 논의한 뒤 바꾸고, PR의 설계/구조 변경에 기록한다.
- 기획서에서 "잠정치"로 표시된 값은 코드에 직접 쓰지 않고 설정값·상수로 둔다.
- 컨벤션과 다르게 작성해야 할 이유가 있으면, 임의로 바꾸지 않고 저장소 소유자와 먼저 논의한다.
- 컨벤션 변경은 PR에 이유와 영향을 기록하고, 기존 구현·실행 방법 변경이 필요한 경우에만 Breaking Change로 표시한다.
- 하나의 기능 작업이 끝나면 [dev-checklist.md](../../dev-checklist.md)의 해당 항목에 진행 결과를 반드시 반영한다. 구현과 필요한 검증이 완료된 항목만 `[x]`로 표시하고 담당자를 기록한다. 일부만 완료했거나 검증이 남았다면 완료 처리하지 않고 현재 상태와 남은 작업을 메모한다. 체크리스트 갱신은 해당 기능 작업에 포함하며, PR을 만드는 경우 같은 PR에 포함한다.
- 작업을 마치면 PR 템플릿의 "다음 작업자가 알아야 할 점"을 채워, 다른 대화창의 에이전트가 맥락을 이어받을 수 있게 한다.
